62. **Task - Intent-driven discovery model** (v0.1.12): Implemented 5-change plan to address systematic benchmark regression (v08 88% -> v17 72%) by providing domain compass during early ontology discovery<br>
    **Result**: The core insight was that the pipeline had no domain compass during the critical first documents when the ontology is being discovered. The intent prompt doesn't seed a fixed schema - it seeds the use case, so the LLM discovers the right ontology naturally. Five structural changes were made to `config.yml`, `types/config.py`, `ontology/buffer.py`, `cli.py`, and `docs/DESIGN.md`, with test fixes in `test_ontology_buffer.py`. (1) Added `ontology_buffer.intent` to `.kg-builder/config.yml` with a CPAP domain use-case statement that propagates to all extraction and curing prompts from doc 1, giving every LLM call domain context for type discovery. (2) Lowered `min_frequency_to_emerge` from 2 to 1, eliminating the 2-document blind spot where docs 1-2 always used the free prompt because no types had reached freq>=2 yet - now all discovered types appear as emerging suggestions in the constrained prompt immediately after first discovery. (3) Changed relationship type filtering in `ontology/buffer.py` `snapshot()` to use `emerge_threshold` (1) instead of `threshold` (2) - relationship types like HAS_SPECIFICATION appear in the constrained prompt after doc 1 instead of requiring two independent discoveries. (4) Removed both `prune_low_frequency_types()` calls before LLM clustering in `cli.py` - pruning at 0.5% of total entities was deleting semantically important low-frequency types (e.g. Mode with 5 entities out of 1400 fell below the 7-entity threshold) that the clustering LLM needs to make good merge decisions. (5) Lowered `min_chao1_coverage` from 0.7 to 0.5 - the previous threshold was never reached in 10-doc corpora (max observed: 0.394), causing curing to only trigger via the safety net at doc 10 rather than through the heuristic detector. Benchmark v18 scored **82% hybrid** (deterministic 60/63=95%, generative 3.4/5.0), up from v17's 71% (55/63=87%, 2.8/5.0). Dimension-by-dimension analysis of why the score improved by 10 points: **document_coverage** jumped from 75% to 100% because v17 had 27 Document nodes (duplicates from safety-net curing at doc 10 where doc/chunk nodes were created both during accumulation and during the flush) while v18 has exactly 10 docs with proper NEXT_CHUNK chains - early curing at doc 4 means 6 documents load directly in cured phase with clean doc/chunk creation. **product_coverage** held at 100% deterministic but generative rose from 3/5 to 4/5 because the intent prompt steered extraction toward product-manufacturer linkages from the first document rather than discovering them incidentally. **cross_doc_resolution** improved from 67% to 83% deterministic - the "same-type name duplicates <= 2" check now passes because removing pre-clustering pruning preserved the type information the clustering LLM needed to consolidate variants like "CPAP Mode" and "Auto Mode" into canonical forms, and singleton types dropped from 12 to <3 because those 12 singletons were artefacts of the old pruning step deleting types the enforcement layer then couldn't match. **relationship_patterns** improved from 75% to 88% - HAS_SPECIFICATION went from 0 to passing because relationship types now enter the constrained prompt at emerge_threshold=1 instead of requiring freq>=2, so doc 2 onwards could produce HAS_SPECIFICATION relationships. SUPPORTS_MODE regressed from 1 to 0, which needs investigation - the relationship type may have been absorbed into a different type during clustering. **type_distribution** went from 80% to 100% - the singleton check now passes (was 12, now <3) because the old prune-before-cluster pipeline created orphan types that couldn't be merged, and all 8 expected ontology types are present with clean distributions (Specification:207, Component:179, Feature:170 as top three). **spec_extraction** generative improved from 2/5 to 4/5 - v17's LLM judge found "many specs lack concrete numeric values" and "all products are null indicating no linkage between specs and actual CPAP devices" while v18's judge found "good coverage across multiple CPAP products with concrete numeric values and proper units" including pressure ranges (4-20 cmH2O), dimensions (116x205x150 mm), sound levels (26.6 dBA) - the intent prompt's mention of "product specifications" and "component architecture" directly guided the LLM to extract structured spec data with values and units. **query_answerability** improved from 80% to 90% deterministic - the DreamStation pressure range query now passes because HAS_SPECIFICATION relationships connect products to their specs. Remaining failures: cross-type duplicates at 56 (threshold <20) where entities like Humidifier, Tube, Mask appear under both Component and Accessory types - this is a genuine semantic ambiguity in the domain that the current cross-type resolution gates (description Jaccard 0.3, embedding cosine 0.75) are too conservative to resolve. SUPPORTS_MODE=0 needs investigation. Generative cross_doc_resolution and query_answerability both scored 2/5 due to the cross-type duplication making the graph appear fragmented to the LLM judge.
