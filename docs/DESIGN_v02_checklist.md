## Corrections

- [x] **#5a - Evidence span config option**: add `evidence_spans: false` to extract config. When enabled, extraction prompt requests character offsets (start, end) into chunk text for each extracted element. Adds latency (larger prompt, structured offset output) but enables exact source traceability. Add `evidence_span` field to entities, relationships, and facts in extraction output format. Add prose explaining the trade-off
- [x] **#5b - Source frequency config option**: add `source_frequency: false` to extract config. When enabled, a post-extraction aggregation pass counts how many independent chunks and documents corroborate each triple. Stored as `source_count` (chunks) and `document_count` (documents) on each entity/relationship. Adds a dedup-time computation step. Add fields to extraction output format. Add prose explaining the trade-off
- [x] **#3 - Three-tier ontology normalization**: rewrite Section 5.2 to replace the single LLM normalization path with three tiers. The end goal is a functioning ontology tree that is proper, acyclic, and ready to be enhanced during generative discovery. After normalization completes, the engine outputs a diagnostic report of the ontology source (type count, relationship count, hierarchy depth, validation issues found and resolved) and prompts the user to confirm before proceeding (continue Y/n in interactive mode, auto-accept in batch mode)
  - [x] **Tier 1 - Programmatic parse with py-repl**: for JSON and other structured formats, the agent uses `py-repl` to write a format-specific parser. The parser extracts entity types, relationship types, properties, and hierarchy from the input. If the parser fails, the agent iterates (adjusts parsing code, retries up to 3 attempts). This handles well-structured inputs without LLM involvement
  - [x] **Tier 2 - LLM-assisted repair**: if Tier 1 succeeds but validation fails (cycles in IS_A hierarchy, dangling relationship targets, orphan types, inconsistent constraints, incomplete property schemas), the LLM receives only the specific issues for targeted repair - not the entire input for re-interpretation. Surgical fixes: "these types form a cycle, which edge to remove?" or "this relationship references type X which does not exist, should it be created or is this a variant?". Hallucination risk is minimal because the LLM is constrained to fixing validated issues, not generating an ontology from scratch
  - [x] **Tier 3 - Full LLM interpretation**: markdown, plain text, prose descriptions, or formats where all Tier 1 parsing attempts failed. This is the existing normalization pipeline - LLM interprets the whole input with Pydantic validation and confidence scoring. Post-normalization validation compares output against source to flag potential hallucinations (type count mismatch, relationship types not mentioned in source text)
  - [x] **Diagnostic output**: after any tier completes, output a summary: source format detected, tier used, types extracted (count), relationships extracted (count), hierarchy depth, validation issues found and how resolved (cycles removed, missing targets created, variants merged). In interactive mode, present to user with continue Y/n. In batch mode, log the diagnostic and auto-accept
